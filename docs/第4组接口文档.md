## 一、接口设计总则

第 4 组向上层（第 1/2/3 组）只暴露**一份工具清单 + 一个调用入口 + 一种返回结构**，全部接口接收结构化的 `(name, params)`，统一返回 `tool_result_json`。

```
上层(Agent / 执行层 / 任务规划)
   │  list_*()                      // 发现能力
   │  call(name, params)            // 调用工具/技能
   ▼
[第4组] ToolRegistry + SkillLibrary
   ├─ 能力层：文件/文件夹/文本/磁盘/系统/应用/浏览器/进程/网络/环境变量
   └─ MockToolRegistry（同构，可整体替换，供跨组联调）
```

### 1.1 与设计书契约的一致性

- 核心返回结构 **`tool_result_json`** 与任务设计书第 4 组契约完全一致；
- 输入 `call(name, params)` 与第 3 组 `ToolClient` 契约对齐（`TOOL_NOT_FOUND`/`TOOL_ERROR` 语义一致）；
- 工具反序列化与 MCP `CallToolResult` 对齐（见「五、MCP 对齐」）。

## 二、输出接口（第 4 组 → 上层）

### 2.1 统一返回结构 tool_result_json

```json
{
  "success": true,         // 或 false
  "result": "...",         // 成功时的结果（字符串 / 结构化对象）
  "error": "..."           // 仅 success=false 时出现
}
```

第 4 组在契约基础上的工程扩展（保证可审计 + 可追踪）：

```json
{
  "success": true,
  "result": "...",
  "tool": "organize_downloads",     // 调用的工具/技能名
  "elapsed_ms": 42,                  // 耗时（供统计/审计）
  "ts": "2026-09-09T09:00:00"        // 时间戳（供第 5 组审计 / RAG）
}
```

### 2.2 返回结构字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| `success` | bool | ✅ | 是否执行成功 |
| `result` | str/object | 成功时 | 执行结果（字符串或结构化对象） |
| `error` | str | 失败时 | 错误描述（`{success:false,error}` 统一） |
| `tool` | str | 扩展 | 实际执行的工具/技能名 |
| `elapsed_ms` | int | 扩展 | 调用耗时（毫秒） |
| `ts` | str | 扩展 | ISO8601 时间戳，供审计/RAG 入库 |

## 三、输入接口（上层 → 第 4 组）

| 接口 | 请求参数 | 返回 | 说明 |
|------|---------|------|------|
| `list_tools()` | — | 工具清单 | 全量工具名 |
| `list_tools_meta()` | — | 清单[{name, description, category}] | 含描述，供规划/展示 |
| `list_tools_mcp()` | — | MCP 格式清单 | 供 MCP 兼容客户端 |
| `list_tools_openai()` | — | OpenAI function 格式 | 直接喂给 function-calling LLM |
| `list_tools_anthropic()` | — | Anthropic 工具格式 | 直接喂给 Claude |
| `list_skills()` | — | 技能清单 | 26 个组合技能 |
| `call(name, params)` | `name`+`params` | tool_result_json | 统一调用工具/技能 |
| `call_safely(name, params)` | 同上 | tool_result_json | 带风险确认门的安全调用 |
| `get_stats()` | — | 调用统计 | 总次数 / 各工具次数 / 最近结果 / Top5 |
| `get_tool_signature(name)` | 工具名 | SHA256 签名 | 工具来源/完整性校验 |
| `list_tool_signatures()` | — | 全部签名 | 批量校验 |
| `verify_tool_integrity(name)` | 工具名 | 校验结果 | 检测注册后是否被篡改 |
| `register(name, func)` / `register_tool` | 名+实现 | 注册成功并自动签名 | 动态扩展 |
| `unregister(name)` | 工具名 | 注销 | 动态收缩 |

### 3.1 call 的分发规则

```
call(name, params)
  ├─ name 是 agent 白名单组合技能 → 走 SkillLibrary（技能编排多层工具）
  ├─ name 是底层工具 → 走 ToolRegistry
  └─ name 未知 → {success:false, error:"工具不存在: <name>"}（TOOL_NOT_FOUND）
```

## 六、错误处理规范

| 错误码语义 | 返回 | 场景示例 |
|-----------|------|---------|
| 成功 | `{success:true, result}` | 操作完成 |
| 工具不存在 | `{success:false, error:"工具不存在: <name>"}` | 未注册工具/技能（TOOL_NOT_FOUND） |
| 参数错误 | `{success:false, error:"缺少必要的参数: <param>"}` | 必填参数缺失/类型错误 |
| 执行异常 | `{success:false, error:"<异常信息>"}` | 底层抛异常，统一归一（TOOL_ERROR） |
| 安全拦截 | `{success:false, error:"危险指令: <cmd>"}` | 命中 DANGEROUS_ACTIONS 直接拒绝 |
| 用户拒绝 | `{success:false, error:"用户拒绝了高危操作: <name>"}` | 确认门被拒/沙箱 check_safe 拒绝 |

**原则**：所有失败统一为 `{success:false, error}`，上层（第 3 组/Agent）无需感知异常类型差异。

## 七、MCP 协议对齐

第 4 组不依赖 MCP serve，但**接口语义与 MCP 对齐**，以便未来无缝接入 MCP 客户端：

| MCP 概念 | 第 4 组对应 |
|---------|-----------|
| `tools/list` | `list_tools_mcp()` |
| `tools/call` + `CallToolResult` | `call(name, params)` → `tool_result_json` |
| Tool Schema（name/description/inputSchema） | `get_tool_spec(name)` / `register` 时由签名自动推导 |
| 资源/提示（resources/prompts） | 本期不实现（工具层聚焦能力） |

## 八、Mock 契约（跨组联调）

- `mock/mock_tools.py`：**57 工具同构** Mock（与正式版同名/同参/同返回 `tool_result_json`）；

## 九、与其它组的对接清单

| 对端组 | 对接物 | 说明 |
|--------|--------|------|
| 第 1 组（AI Shell/HostAgent） | 工具清单 + call | 用户指令 → 意图 → 工具能力落地 |
| 第 2 组（任务规划） | 工具/技能清单 | 规划阶段即知有哪些能力可用 |
| 第 3 组（执行层） | `call(name, params)` → tool_result_json | GUI 或工具二选一时，确定性系统操作走第 4 组 |
| 第 5 组（协调/安全/RAG） | 调用统计 + 审计 ts + 签名 | 审计日志与执行轨迹入库；危险指令硬拦截协同 |
| 全体（联调） | `MockToolRegistry` | 无真实系统时离线复现 |
