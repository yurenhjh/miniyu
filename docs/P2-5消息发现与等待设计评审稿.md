## 一、真实侦察证据（两次运行）

### 迭代 A：正常会话态（report_1789186179858）
- 会话容器：`div.message-list-zLoNs1`，rect≈[280, 56, 757, 643]。
  前缀 `message-list-` 表意稳定，哈希后缀（`-zLoNs1`）随构建变化，不可硬编码。
- user 消息：`align=right`，class 含 `content-*` + `bg-g-send-msg`，气泡文本 `你好`。
- assistant 消息：**无单一稳定节点可锚**。正文是多个 markdown 段落/嵌块（p、多层 div、padding wrapper、action-bar），没有独立稳定的 class/role。
  用内置 `find(role=article/listitem/main/region)` 与 `tag=li` 命中数全部为 0 → ARIA role 结构无法覆盖消息项。
- 读取：容器全文可完整读回（含回复正文 + 时间戳 + 推荐 chips），但要拿「纯 assistant 回复」需做增量/角色分类。

### 迭代 B：落地/欢迎态（report_1789186839909）
- 本次 `message-list-*` **不存在**，容器回退逻辑贪大抓到最大 div（整列含「有什么我能帮你的吗」+ 推荐 chips + 输入框 + 我方 `你好`）。
- 推荐的瞬态 chips（出现又消失）被误判成「assistant 新消息项 7 个」，实为**非回复噪音**。

### 提炼出的两个根因
1. **消息容器锚不稳定**：`message-list-*` 在不同页面态（会话态 vs 落地态）时有时无；贪大回退会抓到错误容器 → 等待与发现全错。
2. **assistant 无「单一气泡」节点**：正文由多个承文块组成，靠「最后一个非用户文本块」会抓错推荐项。

## 二、设计主张：语义增量 + 稳定校验和，不猜 selector

### ① 消息容器锚（Message Root）——确定性发现
按优先级逐级探测，会话内做锚前缀缓存：
1. `<main>` 下**可见** 的 `[class*="message-list"]`
2. 排除 composer（输入区）与推荐区后，可纵向滚动的最大子块
3. 复用本次会话上一次成功的锚 class 前缀（`message-list-*` 前缀本体稳定）

只读这个锚，避免把输入框/推荐文案当消息。

### ② 角色分类（user / assistant）
- user：右对齐（`align=right`）或 class 含 `bg-g-send-msg`。
- assistant：锚内其余**新承文块**（剔除时间戳/日期）。
- 粒度用「承文块 + 增量」，不再追求单气泡节点。

### ③ 等待完成判定（核心）——状态由语义信号驱动
新增原语 `browser_wait_for_change`：
参数：`anchor`（消息根）、`baseline`（发送前根节点 innerText 的 checksum）、`stable_rounds=3`、`stable_interval=1.0s`、`timeout=60s`。

判定「生成完成」= 三者同时满足：
- 根节点 innerText 的 checksum 连续 `stable_rounds` 次采样不变（流式收尾）；
- 不再存在可见的生成中指示（`loading-container-*` / `[aria-busy]` 等）；
- 较发送前 `baseline` 存在文本增量。

返回 = 增量文本（即 assistant 回复）。

### ④ 定向读取
- 对增量承文块逐个贴 `data-miniyu-ref`，`browser_read_text(handle/ref)` 定向读回。
- 多段 markdown → 承文块节点列表逐个读，返回纯 assistant 增量，不再混入推荐 chips。

## 三、建议新增/复用的原语

| 类型 | 名称 | 说明 |
|---|---|---|
| 新增 | `browser_wait_for_change` | 语义等待：checksum 稳定 + loading 消失 + 有增量 |
| 复用 | `browser_find` + handle | 定位输入框/消息锚，现有链路已稳定（含 stale 自动重找 + edit host 下钻） |
| 复用 | `browser_read_text(handle/ref)` | 定向读取增量承文节点 |

设计核心：把「等待」从 LLM 反复推理（5~20 个回合）收敛回 **1 个确定性工具调用**，与 P2-4 的 edit-host 方案同一哲学。

## 四、待 gtp 评审的关键问题

1. **锚的可选策略**是否足够抗落地/会话两种页面态？是否需要额外针对「多会话侧栏 + 主会话」的双容器情况？
2. `checksum 稳定 + loading 消失 + 增量变化` 三信号，是否足以定义「回复完成」？是否需引入「首 token 出现」作为更早的完成起点？
3. 是否要求 `browser_wait_for_change` 在超时/无变化时返回确定性错误（含当前锚校验和），而不是把不确定性抛回模型？
4. 增量的粒度：推荐 chips 常与正文并入同一行，是否需要「正文块 vs 快捷建议块」细分读取边界？
